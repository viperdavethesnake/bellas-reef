# Hub repo split, on-Pi lifecycle scripts, and the install fixes from coco's maiden run

**Date:** 2026-08-30
**Status:** approved in conversation (David, 23:12–23:50 PDT); this document is the written form
**Supersedes:** the deploy model in `docs/superpowers/specs/2026-08-15-hub-first-run-install-design.md` §"Phase 4" (tag derivation) and CLAUDE.md "Deployment discipline" (the `deploy-pi.sh` stop condition)

## 1. Why

`scripts/install-hub.sh` ran on a real Pi 5 for the first time on 2026-08-30
(coco-bellasreef, clean Raspberry Pi OS trixie, 1 GB). It stopped in phase 2.
Working through why exposed four things that are not one-line fixes:

1. **The user's machine is the only machine.** A user gets a Pi, loads an OS,
   clones a repo and runs a script *on the Pi*. `scripts/deploy-pi.sh` and
   `scripts/factory-reset-pi.sh` are workstation→ssh→Pi tools that encode the
   developer's Mac→dev-Pi loop as if it were the product. Ruled: deploy-pi.sh
   "should never have existed" and is deleted; factory reset is something a
   user wants and becomes an on-Pi script; updates become an on-Pi script.
2. **The user's clone is the developer's workshop.** The running hub uses about
   ten files from a 6.4 MB / ~220-file clone: compose, the boot unit, the
   avahi record, the installer, a config example. The rest — source, tests,
   migrations (baked into the images), `docs/superpowers/`, `session-log.md`,
   `CLAUDE.md`, CI, Dockerfiles, `uv.lock` — is ours and was sitting on the
   production hub. Ruled: GitHub's user-facing repo contains only what a user
   deploys.
3. **The installer refuses to finish on a stock image.** It computes the
   correct avahi `allow-interfaces` value and then declines to write it, so a
   clean Pi cannot pass phase 2 without a hand edit. Under "the script is the
   deploy; if the script fails, we fail," that is a script defect.
4. **Several documented prerequisites are neither checked nor performed**
   (`/etc/docker/daemon.json` rotation, the two bind-mount directories), and
   phase 3 prescribes a boot-config paste for an overlay that does not exist
   on a fresh host. Ruled: phase 3 is an inventory — nothing hardware-side is
   required to deploy the stack.

Two things ruled *out of scope* here, recorded so nobody re-opens them by
accident: the GHCR packages stay private until the project is done (the
installer's 401 branch stays; the operator runs `docker login` on the hub),
and the 2 GB RAM floor stays as written until it is measured on coco
(`coco-post-deploy-review-items` memory).

## 2. Shape

Two repositories on GitHub.

| Repo | Contents | Visibility | Written by |
|---|---|---|---|
| `viperdavethesnake/bellas-reef` (this one) | source, tests, CI, specs, CLAUDE.md, Dockerfiles — the workshop | public today; David decides whether to flip it private (see §9) | people, via PRs |
| `viperdavethesnake/bellasreef-hub` (new) | exactly the files a hub runs from, plus a release manifest | private until the project is done | **CI only**, on each `v*` tag; never edited by hand |

The dev repo keeps the source of truth for the hub payload in one directory,
`hub/`, whose contents *are* the hub repo verbatim:

```
hub/
  README.md                       the install guide — first thing a user reads
  LICENSE                         copied from the repo root by the assembler; not in the dev tree
  deploy/
    compose.yaml                  no build: blocks; images by tag only
    .env.example
    release.env                   GENERATED by CI; absent in the dev repo
    systemd/bellasreef.service
    avahi/bellasreef.service
    config/devices.yaml.example
  scripts/
    install-hub.sh
    update-hub.sh                 skeleton (see §6)
    factory-reset-hub.sh
  docs/
    host-setup.md
    hub-platform-requirements.md
    backup-restore.md
```

Everything else in the dev repo stays where it is. `deploy/` in the dev repo
keeps what only a build or a bench needs: the four `Dockerfile.*`,
`compose.drill.yaml` (bench drills, `scripts/drill-restart.sh`), and
`overlays/pwm-4chan.dts`.

Why a directory and not a manifest of paths: a manifest drifts (a file the
installer references but nobody added to the list), a directory cannot.
Inside `hub/`, every relative path is exactly what the user sees on the Pi
— `deploy/compose.yaml`, `scripts/install-hub.sh` — so the operator docs
that move into `hub/docs/` need no path rewriting.

### 2.1 `deploy/release.env` — the release manifest

Three lines, written by the release workflow, never by a person:

```
BELLASREEF_VERSION=v0.2.0-rc.2
BELLASREEF_TAG=<40-hex dev-repo commit the images were built from>
BELLASREEF_CONTRACTS=4.2.0
```

`BELLASREEF_TAG` is what `compose.yaml` interpolates into the image
references, copied into `deploy/.env` by phase 4. The dev repo does not
contain this file; the installer treats its absence as "this is not a
released hub checkout" and stops (§5, phase 4). That replaces today's
`git rev-parse HEAD` + "HEAD is an ancestor of origin/main" derivation,
which only made sense when the clone *was* the dev repo.

### 2.2 `compose.yaml` loses its `build:` blocks

The images are built by CI from the Dockerfiles directly
(`docker/build-push-action`, `file: deploy/Dockerfile.<svc>`); the `build:`
blocks were only ever a local-developer convenience on a machine that has
no container runtime. A user must never build; removing the blocks makes
that structural, and leaves one `compose.yaml` that needs no transformation
between the dev repo and the hub repo. `CONTRIBUTING.md` documents
`docker build -f deploy/Dockerfile.<svc> .` for anyone who wants a local
image.

### 2.3 Two new interpolated paths

`compose.yaml` today bind-mounts `/home/david/backups` and `/etc/bellasreef`
by name and runs the three app services as `1000:1000`. The uid is baked
into the images (`useradd --uid 1000`) and stays. The two paths become
`${BELLASREEF_BACKUP_DIR:?}` and `${BELLASREEF_ETC_DIR:?}`, present in
`.env.example`, written by phase 4 (`$HOME/backups`, `/etc/bellasreef`),
and created by phase 5 owned `1000:1000` (§5). The CI compose-config job
substitutes both, as it already does for the GIDs.

**Existing hub impact:** the dev Pi's `deploy/.env` has neither line, and
its clone is the dev repo. It is down today. When it returns it gets a
fresh install from the hub repo like any other machine — it is the dev/test
hub by ruling (`coco-bellasreef-is-production`), its data is test data, and
phase 1 exits on a machine that is already a hub, so there is no in-place
migration path and this spec deliberately does not invent one. Migrating a
*live* hub between checkouts is `update-hub.sh`'s problem (§6), not the
installer's.

## 3. Release flow

A release is a `v*` tag on the dev repo's `main`. Nothing else produces a
hub-repo commit.

`.github/workflows/release.yaml`, `on: push: tags: ['v*']`:

1. **Retag images — and this is the gate.** `docker buildx imagetools
   create -t ghcr.io/…/bellasreef-<svc>:<version>
   ghcr.io/…/bellasreef-<svc>:<sha>` for the three services. A retag, not
   a rebuild: the release image is bit-for-bit the image CI already
   published for that commit. A missing `<sha>` tag fails the job, which is
   exactly the case to fail on: the tag was pushed to a commit whose CI
   never published (not on `main`, or CI red). No separate API query of
   run status — the image's existence is the evidence.
2. **Assemble.** `scripts/build-hub-repo.sh <outdir> <version> <sha>` copies
   `hub/` to `<outdir>`, writes `deploy/release.env`, copies `LICENSE`. This
   script is the *only* assembler; the workflow calls it and so can a
   developer (the maiden run does, §9).
3. **Publish.** Clone `bellasreef-hub`, replace its working tree with
   `<outdir>` (everything but `.git`), commit `release <version> from
   bellas-reef@<sha>`, tag `<version>`, push branch and tag. History of the
   hub repo is the sequence of releases. Authenticated by a repository
   secret `HUB_REPO_TOKEN` (fine-grained PAT, `contents: write` on
   `bellasreef-hub` only) — a secret only David can create; the workflow
   fails at this step with a message naming it until he does.
4. **Attach.** `bellasreef-hub-<version>.tar.gz` of `<outdir>` is uploaded
   to the GitHub release for the tag (created as a prerelease when the
   version has a `-` suffix). Costs one step and gives a no-git fallback.

Pre-releases (`-rc.N`) go through the same path; `update-hub.sh` (§6) is
where "newest stable vs newest pre-release" is decided, not here.

## 4. The user's journey, end to end

```
git clone https://github.com/viperdavethesnake/bellasreef-hub.git ~/bellasreef
cd ~/bellasreef
./scripts/install-hub.sh
```

While the packages are private, `docker login ghcr.io` before the last line
(`hub/README.md` says so, in a section that is deleted when they go public).
Phase 6 ends with the setup code, the device-import command, and a hub
identity block. Later: `./scripts/update-hub.sh`, `./scripts/factory-reset-hub.sh`.

## 5. `install-hub.sh` — changes by phase

Everything not listed is unchanged. Test names are the acceptance criteria.

**Phase 1 — already deployed.** Unchanged.

**Phase 2 — avahi `allow-interfaces`.** New offer, beside the
service-record one: when the active line is absent and `ih_lan_interfaces()`
returns a value, prompt `set avahi allow-interfaces=<list>?`; on yes,
`sudo` insert the line immediately after the `[server]` header, then
`systemctl restart avahi-daemon` (restart, not reload — interface config is
read at start). The existing re-check pass then sees PASS. No offer when
the list cannot be read or `[server]` is absent (the printed remedy stays,
verbatim). An existing *active* line is never touched; the stock commented
`#allow-interfaces=eth0` is left alone. `--dry-run` prints `would`.
Rationale recorded in the code comment: the list is an *exclusion* of
Docker's bridges, not a choice of the live NIC — a down `eth0` in the
allowlist is inert until plugged in, and omitting it makes the hub
invisible on the day it is. (`test_phase2_offers_to_set_avahi_allow_interfaces`,
`…_declining_leaves_the_printed_remedy`, `…_never_touches_an_existing_line`,
`…_no_offer_without_a_server_section`, `…_dry_run_writes_nothing`)

**Phase 2 — docker log rotation.** New check `ih_check_docker_logging`:
PASS when `/etc/docker/daemon.json` contains a `max-size` under `log-opts`;
otherwise WARN. Remediation offered only when the file is **absent**:
install the documented file (`json-file`, `10m` × `3`) and `systemctl
restart docker`. A present file without rotation is reported with the
documented snippet and left alone — merging a stranger's JSON blind is how
their daemon stops starting. Declining is a WARN, not a FAIL: the stack
runs; the disk fills later. (`test_phase2_offers_docker_log_rotation_when_daemon_json_is_absent`,
`…_reports_but_never_rewrites_an_existing_daemon_json`, `…_decline_is_a_warn_not_a_gate`)

**Phase 3 — inventory only.** Output becomes a report of what this machine
has, one line each, none of them gating:

```
  board        Raspberry Pi 5 Model B Rev 1.1 (RP1 present)
  I2C          bus 1 present; PCA9685 at 0x40: not answering   | answering | not probed (no i2c-tools)
  1-Wire       bus present; DS18B20 probes: 0 (bus up, nothing answering)   | N
  SoC PWM      no pwmchip   | pwmchip present, 4 of 4 header pins muxed | present, no pin muxed
```

The PCA9685 probe is one `i2cget -y 1 0x40 0x00` (MODE1), only when
`i2cget` is on PATH; `0x70` is never addressed. The 1-Wire count is
`28-*` entries; `00-*`-only is called out as a floating bus. Removed: the
`config.txt` paste block, the `dtoverlay=pwm-4chan` line, "reboot and run
this script again", the "proceed with only the interfaces above?" prompt.
The custom-overlay procedure lives in `hub/docs/host-setup.md` §9 for
whoever wants RP1 PWM. (`test_phase3_reports_the_board`,
`test_phase3_probes_for_a_pca9685_when_i2c_tools_exist`,
`test_phase3_counts_ds18b20_probes_and_names_a_floating_bus`,
`test_phase3_never_prescribes_boot_config`, `test_phase3_never_prompts`)

**Phase 4 — configuration.** Tag comes from `deploy/release.env`:
`BELLASREEF_TAG` must be 40 hex, `BELLASREEF_VERSION` must be present; the
PASS line reads `image tag <version> (<sha12>)`. Missing file → FAIL "this
checkout is not a released hub; clone bellasreef-hub" and stop. The
`git status --porcelain` check stays when the checkout is a git work tree
(an edited hub checkout is not a release); a checkout with no `.git` — the
release tarball — gets a WARN "not a git checkout; cannot confirm these
files are unmodified" and continues. The `origin/main` ancestry check and
the "git is required" failure go — git is not needed to read a file. Two new keys written:
`BELLASREEF_BACKUP_DIR=$HOME/backups`, `BELLASREEF_ETC_DIR=/etc/bellasreef`;
the post-write completeness loop covers seven keys. Removed tests:
`test_phase4_pins_the_image_tag_to_the_checkouts_commit`,
`…_refuses_a_commit_that_never_landed_on_main`,
`…_is_unverified_when_origin_main_is_unknown`, `…_fails_without_git`.
Added: `test_phase4_reads_the_tag_from_release_env`,
`…_stops_without_a_release_manifest`, `…_rejects_a_malformed_release_tag`,
`…_writes_the_two_directory_keys`, `…_warns_without_git_metadata_and_continues`.

**Phase 5 — before `up`.** After migrations, before the boot unit:
`sudo install -d -m 0755 -o 1000 -g 1000 "$BELLASREEF_BACKUP_DIR"` and
the same for `"$BELLASREEF_ETC_DIR"` — sudo for both, because chowning to
a uid that is not your own needs it regardless of where the directory
lives. Idempotent; an existing directory is left with its
ownership and reported. No prompt — two empty directories compose.yaml
requires are not a consent-grade action. (`test_phase5_creates_the_bind_mount_directories_owned_by_the_image_uid`,
`…_leaves_existing_directories_alone`)

**Phase 6 — hand-off.** After the setup code (or the "already paired"
line), two additions: the device-import step — where the manifest goes
(`$BELLASREEF_ETC_DIR/devices.import.yaml`, example at
`deploy/config/devices.yaml.example`) and the exact `docker compose … exec
api bellasreef devices import /etc/bellasreef/devices.import.yaml` — and a
hub identity block: hostname, board, RAM, free disk, addresses, version +
tag. (`test_phase6_hands_off_the_device_import_step`,
`test_phase6_prints_the_hub_identity`)

**Watch items for coco's run, not code:** `discover_pwm()` on a Pi 5 with no
`pwmchip` has never executed; coco has zero devices, so the install can
complete but no telemetry exists to verify until a sensor is attached and
imported.

## 6. `update-hub.sh` — skeleton only

Ruled: focus is install. The file ships with `--help`, the phase headers,
and `exit 70` ("not implemented — see the header"). The header records the
design as far as it has been decided so the next session does not
re-derive it:

- Runs on the hub from the hub-repo clone. Refuses an uninstalled hub.
- Moves the checkout to a target ref: default = newest stable `v*` tag
  (no `-` suffix); `--pre` allows the newest pre-release; `--ref <tag>`
  pins. **Open decision, David's:** whether a plain `./scripts/update-hub.sh`
  may ever move to `main` (proposal: no).
- Re-execs itself after the checkout, because the script it is running may
  have changed under it (`--stage2` guard).
- Then: pre-update backup (mandatory, same mechanism as factory reset) →
  `docker compose pull` → `run --rm api alembic upgrade head` → `up -d
  --wait` (only app services change; the data services' definitions do
  not, so `up` leaves them alone) → rewrite `BELLASREEF_TAG` in
  `deploy/.env` → verify.
- Verify has **three outcomes**, not two: PASS (fresh telemetry on the
  wire), NO DEVICES (registry empty — the update is complete; nothing to
  verify; prints the import command; exit 0), FAIL (devices registered,
  nothing on the wire within the deadline). "Green-and-silent" on a hub with
  devices is the outage signal; on a hub without them it is Tuesday.

(`test_update_hub_help_and_not_implemented_exit`, shellcheck-clean.)

## 7. `factory-reset-hub.sh` — on-Pi rewrite

Everything `factory-reset-pi.sh` guards against, kept; only *where it
stands* changes.

- Runs from the hub-repo clone on the hub. `REPO_DIR` from `BASH_SOURCE`.
  `compose()` is `docker compose -f "$REPO_DIR/deploy/compose.yaml"
  --env-file "$REPO_DIR/deploy/.env" "$@"` with `</dev/null` on every
  `exec`, so nothing but the confirmation prompt reads stdin.
- Argument handling first (`-h/--help` → usage, exit 0; anything else →
  usage, exit 1) — the 2026-08-15 lesson stays.
- **Refuses an uninstalled hub** before anything else: no
  `/etc/systemd/system/bellasreef.service` or no non-empty `deploy/.env` →
  "nothing to reset; run install-hub.sh".
- Step 1 backup, mandatory, before the prompt, to
  `/backups/bellasreef-pre-factory-<stamp>.tar.gz`; the host path printed
  is `$BELLASREEF_BACKUP_DIR/<name>` read from `deploy/.env`.
- Step 2 typed `factory-reset`.
- Step 3 `sudo systemctl stop bellasreef.service` → `compose down` →
  assert the three volumes exist (`docker volume ls -q`) → `docker volume
  rm` them. The assert is new: a project-name typo must read "not found",
  not "removed nothing, success".
- Step 4 on-Pi: `compose run --rm api sh -c 'cd /app/db && alembic upgrade
  head'` on the empty volumes, then **`sudo systemctl start
  bellasreef.service`** — the boot unit brings the stack up, so a reset
  also exercises the power-cut path. (`start`, never `restart`; the unit
  is stopped at this point, so `start` is the correct verb and touches
  nothing that is running.)
- Step 5 verification unchanged in substance, against `127.0.0.1:8000`:
  `/api/v1/info` answers within 30 s; `paired_client_count` 0; `setup_mode`
  true; `devices` and `audit_log` counts 0 via `psql` inside the postgres
  container; `alembic current` at head; 7 `stream created` lines within
  60 s; ≥1 `capability announced` within 60 s. The last assertion is a
  **watch item**: a hub with no hardware may legitimately announce nothing
  under the phase-3 ruling; if coco shows that, it becomes "announced N
  (0 is fine with no hardware)" in a follow-up, not weakened pre-emptively.
- Step 6 mint the setup code, last thing on screen.

`factory-reset-pi.sh` deleted. CLAUDE.md's "sanctioned exception" paragraph
names the new script. Tests in `tests/test_factory_reset_hub.py` on the
shared harness (§8): `--help`/unknown-arg exit before anything runs;
refusal on an uninstalled hub; backup fires before the prompt; a declined
prompt touches nothing after the backup; destructive order (stop → down →
volume assert → rm); redeploy uses `systemctl start`; each step-5 assertion
fails the run when its stub returns the wrong value.
